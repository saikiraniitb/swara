# Qwen3-TTS speech tokenizer

## Answer: is it stronger than Dia + DAC for Swara?

**CONDITIONAL YES.** Qwen's released 12.5 Hz/16-codebook tokenizer is a stronger technical starting point for a low-latency, long-form Swara engine than Dia's DAC path, because it reduces outer autoregressive time steps by roughly 6.9x relative to Dia's documented ~86 audio tokens/sec and has a causal chunked decoder. It is conditional on a source-level license and quality review with Indian voices before shipping; no such evaluation was run here.

## Released 12 Hz family

- The current released tokenizer is named “12Hz”; its model card specifies **12.5 Hz**, 16 layers/codebooks. Source configuration uses 24,000 Hz audio and 1,920 samples/frame (`24000 / 1920 = 12.5`).
- Encoder: Hugging Face `MimiModel` encoder plus a split residual vector quantizer. The configured valid output is 16 quantizers. Source names an `n_semantic_q` split inside `SplitResidualVectorQuantizer`; that is structural evidence that the representation separates semantic-first and residual/acoustic quantization, but the public config/checkpoint is absent here, so the exact semantic/acoustic allocation is not known.
- Decoder: quantizer decode -> pre-convolution -> causal transformer -> causal ConvNeXt/upsampling stages -> causal output convolution. It is explicitly non-DiT.
- Encode returns `(frames, 16)` discrete codes. Decode clamps codes, invokes `chunked_decode(chunk_size=300, left_context_size=25)`, and trims waveform length. At 12.5 Hz, a 300-frame decode chunk is 24 seconds with 2 seconds of left code context.
- Raw token events are 200 indices/sec (12.5 × 16), but the expensive **main sequence length** is 12.5 frames/sec. The 15 residual codes are generated by the within-frame predictor.

This codec is separately trained from the TTS model in the visible inference/SFT path: it is loaded as a pretrained tokenizer and SFT consumes precomputed codes. Public source does not expose tokenizer training code, so joint training must not be assumed.

## 25 Hz code retained in the repository

The repository retains a prior `tokenizer_25hz` implementation. It has a WhisperEncoderVQ path and decoder configuration classes for DiT/BigVGAN. It is not the released 12 Hz product path selected by the README and model cards. Do not build Swara around it merely because its code remains in-tree.

## Streaming and storage implications

The causal decoder and 25-frame left context make chunked waveform reconstruction feasible. Low outer-frame rate lowers Talker KV-cache growth and allows packetization by frames. It does not make generation fully parallel: the sub-talker adds 15 serial categorical selections to every frame. Storage is 200 code indices/sec before packing/entropy coding; actual bytes depend on vocabulary cardinality and format.

## Contrast with Dia + DAC

Dia uses an external Descript Audio Codec model and generates delayed multi-codebook DAC streams. The Dia README says approximately 86 tokens/sec for its audio prompt, and its model source implements codebook delay/revert logic. Qwen owns the speech tokenizer interface and its causal decoder in the same codebase, with low-rate frames and a purpose-built residual-code predictor. Dia's DAC remains a credible standalone codec, but is not architecturally aligned with explicit speaker-vector and low-rate Qwen generation.

## Reuse decision

**Adapt/evaluate Qwen's tokenizer design; do not bind Swara to its checkpoint before Indian-language reconstruction and license validation.** Preserve the 12.5 Hz multi-codebook interface and causal chunk decoder concept. Reimplement any tokenizer training and deployment wrapper Swara needs.

Evidence: `qwen_tts/core/tokenizer_12hz/{configuration_qwen3_tts_tokenizer_v2.py,modeling_qwen3_tts_tokenizer_v2.py}`; `qwen_tts/core/tokenizer_25hz/*`; Qwen tokenizer model card (license and 12.5 Hz/16-layer statement).
